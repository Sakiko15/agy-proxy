## 演练揪出的测量/引擎缺陷（五条，均已修复并复跑）

首轮 1h soak 的判定结果不成立——诊断定位出 **harness 四个测量缺陷 + 一个引擎缺陷**（用 3×2~3min 诊断跑 + 池状态快照 + 20min RSS 探针逐一定案，修复后重跑正式 1h）：

1. **[harness] stream 车道的「100% ok」是假象**：SSE 响应经 `reply.hijack()` 后 **200 头在引擎调用之前发出**，引擎失败（含 429 POOL_EXHAUSTED）以**流内 error 负载**到达。harness 原来只看 HTTP status → 失败也记成 ok；plain 车道（完整引擎执行后才响应）才反映真相。修复：stream 车道按**流体内容**判定（含 `"error"` 帧即失败），修复后 stream 与 plain 车道判定一致（如 stream{200=36,500=320} vs plain{200=36,429=308}）。**此前所有 soak 的 stream-lane 进度判定均因此虚高**——包括更早的 2min 23/23 PASS。
2. **[harness] 失败窗口善后需结算宽限**：rate-limit 窗口（15s）冷却全部账号 21m25s；调度器窗口末 clear 后，**在飞请求的 settlement 滞后 2~5s 落账**——重新冷却账号（引擎行为正确：账号确实收到 429；429+Retry-After 正是 charter §6 的 M3 定案语义），池即刻再次耗尽。诊断证据：429 报文 "earliest reset in 1295s" **大于** fake 全额冷却 1285s，即 clear 之后新产生的冷却；快照显示 3 账号 `cooldowns.google` 全部活跃、consecutiveFailures 3/1/1。修复：窗口末先翻回 ok 模式，**12s 结算宽限（仍计入窗口内）后再 clear**，滞尾不再污染判分。
3. **[harness] 句柄判定负载敏感**：原判「late 全窗 max vs early 全窗 min（容差 5）」把并发抬升的句柄天花板当成了泄漏——1h 首跑 early min=6 → late max=12 判 FAIL。分桶数据（每 10% run 输出 min/p50/max）显示**地板 p50 稳定**（7→8 后全程持平 7 桶）、天花板随负载振荡回落——是并发相关波动而非棘轮泄漏。修复：判定改为**分桶 p50 地板**（late p50 ≤ early p50 + 3），分桶轨迹保留打印供人读。
4. **[引擎] busy-aware 铺开从未生效（commit ec17a1a 修复）**：perf 腿 6 在空闲机器上仍测得 ~2.0×，新增的逐发 accountId 诊断显示三个并行请求**叠在单账号 spacing 闸后**——追查发现 M5 的 busy 跟踪是 **stream() 内的局部 Set**，跨请求不可见（f764c0d 的 2.7× 是时序运气）。修复：busyAccounts/inFlightCount 提升为引擎实例字段（共享 Set + 引用计数），补并发铺开单测（三发并发同族流必须落三个不同 accountId——修复前该断言值为 1）。修复效果（1h soak 实测）：每车道真实成功 890 → **2660**，spawn 总数 3927 → **9639**（约 2.5× 的真实服务量，P1 车道并发三账号真铺开）。
5. **[harness] RSS 判定器语义修正（20min 探针定案）**：引擎修复使真实服务量约 3× 后，RSS 斜率判定从 1% 升到 7%/23% 判 FAIL。20 分钟带样本 dump 的探针给出铁证：RSS 分桶轨迹是**锯齿**——爬升至 V8 堆高水位 ~248M（前 ~12 分钟）后**回落**至 159–175M（最后 20%）。泄漏不可能回落；原「中段 vs 尾段中位数斜率」判定踩在锯齿不同相位上。修复：判定改为**不棘轮**（尾桶 p50 ≤ 历史峰值桶 p50 + 16MB 容差；棘轮式泄漏每桶都创新高且永不回落，锯齿工作集必然回落），分桶轨迹保留打印，斜率数值降为信息项。慢于锯齿幅度的缓漏由 48h VPS 长跑承担（本闸 1h 窗口对此不设防，如实注明）。

**引擎侧语义核对（正确，未改动）**：POOL_EXHAUSTED 429 + Retry-After、结算滞后重冷却（账号确实收到 429，冷却合理）、P2 错误矩阵 7/7、P3 强杀对账 10/10 各轮均 PASS。另把 `scripts/` 纳入 `npm run check` 闸（一处 harness ReferenceError 曾逃逸类型检查）。

## 错误矩阵引擎语义（与 P2 互证的单测钉）

| 场景 | fake-agy 模式 | 期望行为（单测钉） |
|---|---|---|
| 进程早死（无输出） | `kill-early` | 重试救回：2 次 spawn，无客户端可见输出，最终成功 |
| 进程中死（有部分输出） | `kill-mid` | **不重放**：单 spawn，部分文本照达客户端后 PROCESS_EXIT 结束 |
| exit 1 + 错误信封 | `exit-error` | 不重试（INVALID_OUTPUT 非「无结果空响应」形态），真错误透传 |
| hung | `hang` | 看门狗 TIMEOUT → 重试一次 |
| auth 失败 | `auth` | AUTH 分类，不重试（凭据问题是确定性的） |
| 429 硬限流 | `rate-limit` | 502 限流族 + 账号冷却，不重试（M3 决策：in-flight 失败，下一请求切换） |
| VALIDATION_REQUIRED | `validation` | 403 + validation_url 透传 + 账号隔离（唯一可经 `/admin/pool/accounts/:id/clear-auth` 恢复） |

**强杀语义双平台记录**（engine-retry.test.ts:192 平台分支钉）：win32（本机活体）= `agy exited with code 1`（TerminateProcess，无 signal）；POSIX = `terminated (signal SIGKILL)`（进程组 `process.kill(-pid)`）。两者同分类 `Err.PROCESS_EXIT`。POSIX 的活体观察在 Linux 容器内进行 → **待用户**（与 P3 docker kill 腿合并执行）。
